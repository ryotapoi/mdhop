# 情報管理の原則

## 目的

コードから推測すると間違える意図と、毎回導出するのが割に合わないものだけを文書に残す。置いた文書を信用できず、結局リポジトリを調べ直すなら、その文書は置く意味がない。必要なものは漏れなく、しかし最小限に保つ。書き手が人か AI かは区別の根拠にならない。
プロジェクト管理（スケジュール等）、ハーネス固有の使い方、ビルドに書き出す前の素材（デザインデータ等）は対象外とする。

## 3原則

### 1. 実体だけを書き、説明は書かない

Markdown は実行されないコードとして扱う。実体はその物事の唯一の表現であり、説明は他の実体の言い換えである。言い換えは必ず実体からずれる。モデルがすでに知っている一般論も説明に当たる。ただし、一般的な選択肢のうちこのプロジェクトがどれを選んだかは実体である。
判定の問い：これが消えたら、その内容はどこにも残らないか。

### 2. 時制を混ぜない

コミットされたものは現在である。現在でないものだけを、本文を読まずに置き場かフロントマターで見分けられるようにする。

| 時制 | 置き場 |
|---|---|
| 過去 | `status: superseded` の ADR、git 履歴 |
| 未来 | `backlog/`（未着手のタスクと、完了したが版に入っていないタスク） |
| 生成時点 | `cache/` |

現在のファイルに、もう有効でない記述やまだ有効でない記述を混ぜない。いつ変わったかは git が持つ。
判定の問い：このファイルが今も有効かどうかを、本文を読まずに言えるか。

### 3. 必要になる瞬間に目に入る場所に置く

置き場は「この種類のフォルダが要るか」ではなく「いつ読まれるべきか」で決め、フォルダ構成はその結果とする。理由は実体の隣に書く。コードの判断はそのコードのコメント、要件はその項目に1行、手順はその手順の横に置き、実体と理由を分けない。
判定の問い：この情報を必要とする作業で、エージェントはこのファイルを開くか。開かないなら、開く場所へ移すか、`AGENTS.md` の案内を足す。

## 何をどこに書くか

| 問い | 置き場 |
|---|---|
| 何のために作るか、何をしないか、守る制約 | `docs/requirements.md` |
| どう作ると決めたか、なぜか（理由を添える実体が一つに定まらない判断） | `decisions/` の current の ADR |
| どう動くか（How） | コード |
| 何を約束するか（What） | テスト |
| この箇所はなぜこう書き、なぜ他の書き方でないか（Why not） | コードコメント |
| この変更はなぜしたか（変更の Why） | コミットメッセージ |
| どう作業するか（リリース、検証など） | `docs/<作業名>.md` |
| 複数の実装や他者が従う取り決め | `docs/<名前>.md` |
| これから何をするか | `backlog/` |
| 導出できるが毎回導出するのが割に合わないもの | `cache/` |
| 以前どう判断していたか | superseded の ADR、git 履歴 |
| 利用者に見せる形 | README・ヘルプ等の成果物 |

## 一般的なやり方と違う点

ADR は、理由を添えるべき実体が一つに定まらない判断（使用言語、全モジュールにまたがる方針など）だけに書く。ADR は今効いている判断であり、実装済みかどうかとは関係ない。判断した時点で書き、実装を待たない。置き場はリポジトリ直下の `decisions/` である。フロントマターの `status` は `current` か `superseded` の2択で、置き換え先があれば `superseded_by` を付ける。判断が間違っていた、または方針が変わったら、旧 ADR を丸ごと superseded にし、引き続き有効な部分も含めて新 ADR に全部書き直す。current の ADR だけを読めば今の判断が揃う状態を保つためである。その他のフロントマターと本文の節構成は規定しない。
判定の問い：この判断の理由を1か所に添えるなら、どこか。定まるならそこに書き、定まらなければ ADR にする。

仕様書は、コードを言い換えたものなら書かない。実装済みの振る舞いはコード、約束はテスト、利用者向けの形は成果物、未実装の仕様は backlog の項目、上位の意図は要件が持つ。仕様書そのものが実体である場合、つまり複数の実装が従う共通仕様、外部に公開するファイル形式やプロトコル、実装より先に他者と合意が必要な取り決めは置く。「仕様書」という名前ではなく、原則1の問いで決める。
判定の問い：この文書が消えたとき、同じ内容をコードとテストから復元できるか。できるなら書かない。

キャッシュは `cache/` に置き、必要なら配下を分ける。導出手順（コマンド、またはプロンプト相当）と生成時のコミットを、そのファイルのフロントマターか、まとまりの中の1ファイルに書く。最新であることは保証せず、必要なら作り直す。機械的な一致検査は要求しない。コードの地図や概念ガイドもコードの言い換えなので、置くならキャッシュとして置く。

backlog は `backlog/backlog.md` を基本とし、必要なら `backlog/` 配下にファイルを足す。書くのはタスクだけで、気づいたことは調べて決める調査タスクにする。完了したタスクは `- [x]` にして残し、版を切る変更（バージョンを上げてタグを打つ変更）で消す。外部に配るなら、同じ変更で CHANGELOG に書く。その版で完了したタスクがタグの付いたコミットの差分に揃い、残すべき内容（理由、守るべき制約）がコード・テスト・`docs/`・ADR へ移っているかを、消す前にまとめて確かめられるためである。取りやめたタスクは `[x]` にせず消す。backlog を持つプロジェクトは版を切る。その他の運用は自由とする。

`.tmp/` はコミットしない作業用フォルダであり、必ず gitignore する。いつ消えても壊れないものだけを置く。

`AGENTS.md` は常に読まれる入口であり、作業ごとに何を読むかを案内する。常に読むべき内容も、名前を付けた別ファイルに置いて `AGENTS.md` から参照し、`AGENTS.md` 自体に実体を溜めない。

今後も守るべきことは、コミットメッセージだけに置かない。エージェントは履歴を自分から引かないので、そこにしかない制約は守られない。

## 置き場を増やす条件

時制か読まれる瞬間が、既存のどの置き場とも違うときだけ増やす。主題の違いや量は、置き場の中をファイルやフォルダに分ける理由にはなるが、置き場を増やす理由にはしない。
