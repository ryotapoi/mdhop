# v0.21.0 関連表示と 2-hop のフィルタ整理

[Backlog のタスク](backlog.md#v0210-関連表示と-2-hop-のフィルタ整理)の実装に向けた要求、合意済みの方針、未決事項、受入条件を記す。このファイルは現行仕様の正本ではない。現在の振る舞いは [CLI 仕様](../docs/specs/overview.md)、データモデルは [データモデル](../docs/rules/03-data-model.md)、責務の境界は [アーキテクチャ](../docs/rules/architecture.md)を参照する。実装時に確定した振る舞いは正本へ反映する。

## 目的と範囲

開いている Markdown ファイル B の関連ノートを読むとき、一覧から対象を隠す操作と、関連性の根拠となる共通ターゲットを選ぶ操作を独立させる。2-hop は `B → X ← C` の共通ターゲット方式とし、X を手がかり、C を関連ノートとして返す。通常の backlinks / outgoing に via の概念は導入しない。backlinks は B へリンクするノート、outgoing は B が参照する note / asset / phantom、tags は B が持つタグとして扱う。

既存の SQLite スキーマ、索引済みのグラフと保存形式は変更しない。query 時に保存済みの関係を選択・表示する。`build.exclude_paths` と、そこから除外されたファイルへの参照の現行動作も変更しない。索引対象外の関係を表示操作から復元する新機能は設けず、このタスクのための索引 migration や再 build も要求しない。

主な入口は Markdown ファイル B とする。既存の tag / phantom / asset など非 note 入口では inbound seed の現行動作を確認し、必要な互換性を定める。B を指定せず X の inbound 全体を探す操作、入口なしの検索、新しい探索方式は追加しない。外部 URL の非表示や索引化も扱わない。

既存仕様の変更を許容し、後方互換性の維持を必須にしない。CLI / config / JSON の名称、意味、形式は要求に合わせて変更できる。旧仕様の別名や互換処理を残すことは必須としない。個別機能の削除は、それぞれ必要性を判断する。

## 合意済みの動作

### 表示と手がかりの分離

- パス条件に一致する Markdown ファイルと、タグを関連表示から隠せるようにする。タグを隠しても、そのタグを持つノート全体は隠さない。
- 表示非表示は 2-hop の関係計算を変えない。X を表示から隠しても X 経由の C は残る。C 自身を隠した場合は C を表示しない。同じノートが backlinks / outgoing / twohop に現れる場合は一貫して隠す。
- パスによる表示条件は Markdown ファイルを対象とし、asset / phantom の非表示へ暗黙に拡張しない。対象 node 型と、パスを持たない node の扱いは実装前に確定する。
- 表示とは別の条件で、2-hop の X に使うパス・タグを包含または除外できる。条件未指定なら通常の共通ターゲット探索を保つ。X を手がかりから除いても、通常の outgoing の表示は消さない。
- パスパターンの包含に加え、単一の X を型つきで明示指定できる。B が X を参照しなければ空結果とし、別の X へ fallback しない。同じ綴りの note と tag は区別する。
- 複数の包含条件は OR、除外条件はいずれかに一致すれば除外を優先する。表示から隠した X を手がかりに選ぶこともできる。

### config と CLI の合成

- 表示から隠す条件と 2-hop の手がかりを除く条件は、config と CLI の両方で独立した目的として指定する。それぞれパス条件とタグ条件を独立して指定できる。
- 各目的では config の条件と CLI の条件を既定で加算する。CLI でパス条件だけを指定しても、config のタグ条件は残る。逆も同じ。一方の目的の指定は、もう一方の目的に影響しない。
- 各目的に、**その目的の config 条件だけ**を無視する CLI 操作を設ける。単独指定ならその目的の除外条件は空になり、CLI 条件と併用すれば CLI 条件だけを使う。他方の目的の config 条件と CLI 条件は維持する。名称は「非表示をすべて解除する」と誤読されず、config の無視を表すものにする。
- 既存 YAML の `exclude` は、**新しい手がかり除外の config 項目が未記載の場合に限り**、読み込み時に手がかり除外の既定値として使う。新項目が明記されていれば、空リストでも新項目を優先する。YAML の自動書き換え、専用 migration コマンド、移行警告・エラー、JSON の移行フィールドは必須にしない。この fallback は小さな読込時処理にとどめる。
- 旧 `exclude` は従来、2-hop の via だけでなく targets、tags 表示などにも効いていた。手がかり除外への読込時 fallback はその意味を完全には維持しない。この変更と設定の移し方を利用者へ説明する。`search` は旧 `exclude` 設定を読む現行動作を維持し、query の新しい意味を他コマンドへ自動的に広げない。

### 条件と対象範囲

- 同種のパス条件は Vault 相対パス・正規化と現行 glob を起点に共通の照合規則を使う。`*` は `/` を含む任意文字列、`?` は一文字、case-sensitive、`[...]` は非対応とする。タグは `#` の正規化と case-insensitive な完全一致を起点にする。
- 任意の名前正規表現や新しいメタデータ条件は追加しない。既存の `--path` / `--where` は結果ノード側の条件で、via 選択ではない。今回の要求だけを理由に既存機能を一括削除しない。
- frontmatter 由来の通常リンクは、設定された raw path を含め、本文リンクと同じ関係として扱う。リンクになっていない通常の frontmatter 値から関係を作らない。frontmatter 専用の非表示操作や meta / head / snippet の設計変更は追加しない。`--link-key` は現行どおり direct な backlinks / outgoing のみを対象とし、残す場合は新条件との組み合わせを確認する。
- 共有 helper を使う search / diagnose / reachable / graph などを query と同じ名称・意味へ自動的に変更しない。直接影響する契約だけを扱う。

## 実装前に確定する事項

- 表示・手がかり条件、単一 X 指定、新旧 CLI の移行に使うフラグ名と構文。config の新項目名、個別タグを隠す操作と tags 表示全体を隠す操作の採否。名前案だけで採用を確定しない。
- 入口 B 自身が表示条件に一致した場合の扱い（現行は入口を除外しない）、note / asset / phantom / tag の各適用範囲、非 note 入口の互換性。
- 隠した X を露出せずに C と関連理由を表す JSON / text 形式。C に複数の手がかりがある場合、表示可能・非表示の手がかりが混在する場合、すべて非表示の場合の理由、重複、グループ表現。X の代替表示や匿名化は未決。
- 手がかり選択、表示条件、既存の結果条件、並び順、`--max-backlinks` / `--max-twohop` / `--max-via-per-target` の適用順と件数。非表示結果や空グループが上限枠を消費し、後続の有効な結果が欠落しないようにする。
- 旧 CLI オプションの意味変更・別名維持・削除の扱い。旧 CLI の別名を残すことは必須ではない。利用者に必要な移行方法を明記する。

## 受入条件

- v0.20.0 で作成した索引を再 build せずに利用でき、表示・手がかりの設定変更でも再 build を要求しない。`build.exclude_paths` で索引対象から除外したファイルへの参照は、現行と同じ扱いになる。
- `B → X ← C` と `B → Y ← D` を基本 fixture とし、X を `archive/X.md` に置く。条件未指定時は現行の関係を取得する。X だけ隠しても C は残り、C を隠すと C は消える。X を手がかりから除くと X 経由の C は消えて Y 経由の D は残る。X を明示すると C のみ取得する。
- B が参照しない X を明示すると空結果になる。単一 X と glob 包含、同じ綴りの note / tag を区別できる。B と C が X と Y の双方を共有する場合、包含の OR、除外優先、表示条件との合成に従って C が残るか消えるか確認する。
- 共通タグ `#daily` を持つ B と C で、タグの表示だけを隠しても C は残り、手がかりのタグ除外ではそのタグ経由の関連が消える。タグを隠しても、そのタグを持つ通常の backlinks / outgoing ノートを一律には隠さない。
- config と CLI の加算を二つの目的ごとに検証する。パスのみ・タグのみの CLI 指定でも他方の config 条件が残る。目的ごとの config 無視を単独指定した場合と CLI 条件と併用した場合、他方の目的が維持される場合を確認する。旧 `exclude` だけ、新項目だけ、両方記載、新項目が空の場合の優先順位と `search` の旧設定を確認する。
- 本文と frontmatter の通常リンクで同じ条件が同じ結果を返し、frontmatter の通常値から関係を作らない。`--link-key` / `--path` / `--where` の直接影響する既存契約を確認する。
- 非表示結果や空グループが上限より前に多数あっても、有効結果を上限まで取得できる。複数手がかりと非表示の手がかりだけが残る場合について、確定した理由表現、順序、件数を確認する。
- パスの大小文字・`/` を含む glob・非対応文字クラス、タグの `#` 有無・大小文字、適用対象 node 型の正常系・異常系を確認する。stdout の JSON は単独で parse でき、付加情報は stderr に出す。query は索引やファイルを変更しない。

## 実装の入口と完了条件

主な入口は `internal/core/query.go` / `query_fetch.go`、`exclude_filter.go` / `pathfilter.go`、`cmd/mdhop/query.go` / `format_query.go` と関連 query test。保存形式は変えず、query 時の選択と出力に必要な最小の整合した変更を行う。

採用した振る舞いと利用者に必要な移行方法を [CLI 仕様](../docs/specs/overview.md)などの正本に反映する。判断理由を残す必要があれば `docs/decisions/` の運用に従う。この backlog 文書を恒久仕様として扱わない。[検証ルール](../docs/rules/verification.md)に従い、集中 test、`go test ./...`、`go build ./...` と実バイナリの CLI 確認を行う。
