# Goal Decisions

ユーザー意図と違う可能性がある自動判断の記録。マスターが後でまとめて確認する。

## Format

各エントリは選択肢ベースで書く。マスターが「今回の選択が妥当か / 妥当でないか」を判断できる形にする。

```
### YYYY-MM-DD HH:mm - <判断タイトル>

- 対象タスク:
- 論点: 何を選ぶ必要があったか（短く）
- 選択肢:
  - 案A: 〜 — こういう設計判断 / タスク管理を優先するなら案A
  - 案B: 〜 — こういう設計判断 / タスク管理を優先するなら案B
- 選んだ案: 案X
- 理由: 〜
```

書き方のルール:

- 「選択肢」は実際に検討したものを書く（後付けで作らない）
- 各案の判断軸は **設計判断 / タスク管理レベル** で書く
  - 設計判断の例: 「YAGNI を優先 / 後の手戻り回避を優先」「整合性を優先 / 局所修正を優先」「型安全を優先 / シグネチャ変更回避を優先」
  - タスク管理の例: 「今のタスクで一緒にやる / 別タスクに切る」「v0.6.1 のスコープを守る / スコープを広げる」「即時解消 / 横断対応待ち」
  - コードレベル（「`fmt.Sprintf` を使う / 使わない」「変数名を X にする / Y にする」）には落とさない
- 「理由」は選んだ理由・選ばなかった理由のどちらか / 両方を必要なだけ書く（項目は分けない）
- 「ユーザー意図と違う可能性」「後で確認してほしい点」「派生アクション」のような曖昧な項目は書かない。選択肢と理由が読めればマスターが判断できる
- マスターが「妥当」と返せば履歴として残るだけ、「妥当でない」と返せばマスター指示で別タスク化や修正コミットが入る

### 2026-05-06 19:30 - ノード型定数化を untyped const に絞る

- 対象タスク: v0.6.1「ノード型文字列リテラル定数化」
- 論点: design レビューで `type NodeType string` の named type 化を SHOULD 指摘。今回タスクに含めるか
- 選択肢:
  - 案A: untyped string const のみで定数化を完結 — 今回タスクのスコープ（定数化）を守り、型強化は別タスクに切るタスク管理を優先するなら案A
  - 案B: named type 化までセットでやる — 型安全を最大化し、後続タスクへの分割コストを避ける設計判断を優先するなら案B
- 選んだ案: 案A
- 理由: 案B は `upsertNode` 等のシグネチャ変更がテスト・DB スキャン結果マッピングに波及し、1 コミットの粒度を超える。goal.md の Constraints「v0.6.1 の範囲外の unrelated refactor はやらない」に反するため切り出す。named type 化は v0.7.0 以降の別タスクに分けることで案B の価値も後続で実現できる

### 2026-05-06 19:30 - SQL 内シングルクォートリテラルは const 化対象外

- 対象タスク: v0.6.1「ノード型文字列リテラル定数化」
- 論点: `db.go:153 'phantom'`, `:184 'tag'`, `:330 'phantom'`, `:357 'tag','phantom','asset'` の SQL 内シングルクォートを定数化対象に含めるか
- 選択肢:
  - 案A: SQL 内シングルクォートは対象外。Intent を「Go コード側のタイポ検出」に絞る — タスクスコープを Go 側に限定し、SQL は別空間として扱う設計判断を優先するなら案A
  - 案B: SQL 内も統一する（動的生成 or bind 変数化） — Go と SQL で値表現を完全に揃え、内部コア全体の一貫性を最大化する設計判断を優先するなら案B
- 選んだ案: 案A
- 理由: 案B は既存の RAW SQL 文字列パターンを崩し、SQL injection 対策・可読性の観点で複雑度が上がる。SQL 側のタイポは現状実害として顕在化しておらず、横断対応する根拠が薄い（YAGNI）。Go コード側のタイポ検出という今回タスクの Intent は案A で達成できる

### 2026-05-06 20:10 - query_entry.go の `sql.ErrNoRows == 比較` を今回タスクで修正しない

- 対象タスク: v0.6.1「`internal/core/query.go` をエントリ解決とデータフェッチに分離」
- 論点: review-code go 観点で `query_entry.go:47` `:70` の `err == sql.ErrNoRows` を `errors.Is(err, sql.ErrNoRows)` に直す 🔴 MUST 指摘。今回タスクで対応するか
- 選択肢:
  - 案A: 当該 2 箇所だけ即時修正 — レビュー指摘を即時解消することを優先するなら案A
  - 案B: 今回タスクでは無修正で持ち越し、v0.7.0「sentinel error 化」タスクで横断対応 — 物理分割タスクの Intent を守り、エラー扱いの修正は横断 1 タスクで完結させる横断対応待ちのタスク管理を優先するなら案B
- 選んだ案: 案B
- 理由: 案A は `internal/core` 全体 13 箇所の `==` 比較のうち 2 箇所だけ部分修正することになり、残り 11 箇所と一貫性が崩れる。当該 `==` 比較は元コードからの持ち越しで新規に持ち込んだ問題ではなく、今回タスクの Intent（物理分割）の範囲外。v0.7.0「sentinel error 化」タスク（backlog.md L50-52）が既に登録済みで、横断対応の受け皿は確保されている
