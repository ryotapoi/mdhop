### v0.22.0

- [x] 設定形式を TOML に変更する

  目的: 索引・探索・frontmatter の設定を TOML で読み書きできるようにする。TOML に Vault・DB のパスを指定する機能は設けない。

  対応: `github.com/pelletier/go-toml/v2` を使う。既定ファイル名を `mdhop.toml` とし、既存の build 除外、search 除外、query の hide / via、meta の types / ordered / profiles / link_keys の意味を保つ。`query.via.exclude` の未指定と明示空の区別も維持する。`init-meta` の標準出力と `--write` を TOML に対応させ、既存の他の設定を保って型定義を生成・更新する。通常のコマンドは YAML 設定を読み込まず、暗黙の変換や削除もしない。ノートの YAML frontmatter は引き続き扱う。旧設定の変換は別タスクの `migrate` が担う。

  受入条件: 既存の各設定が TOML でも同じ意味で動作し、設定なしなら既定値で動作する。`init-meta` の生成・更新が TOML として利用できる。CLI ヘルプ・README・設定例・関連する現行 ADR・依存のライセンス通知を更新する。

- [x] Vault・索引 DB・設定ファイルを CLI 引数で独立して指定できるようにする

  目的: 対象フォルダと DB・設定の置き場所を利用者が独立して選べるようにする。

  操作: `--vault`・`--db`・`--config` を DB・設定を扱う全コマンドで一貫して使い、生成・参照・更新・診断・設定書き出しに反映する。専用の移行操作である `migrate` は後述の固定配置を使い、`--vault` のみ受け付ける。Vault は探索・リンク解釈・本文参照・出力パスの基準であり、DB や設定の場所から推定しない。`--vault` がなければカレントディレクトリを使う。CLI のパス引数は絶対パス・相対パスを受け付け、相対パスはカレントディレクトリ基準とする。設定内の除外パターン等は設定ファイルの場所によらず Vault 基準とする。

  設定の選択: `--config` があれば指定ファイルだけを読み、なければ `<vault>/mdhop.toml` だけを読む。既定ファイルが存在しなければ設定なしで動作する。既定ファイルとの併読・マージや、任意名のファイルの自動検出はしない。明示指定の欠落、明示・既定いずれの設定でも読み取り失敗や不正な内容はエラーにする。`--no-config` は追加しない。

  書き込みと置換: `--db` があればその DB を使い、未指定時は別タスクの既定保存先に従う。DB に伴う書き込みは DB 側、設定の明示的な書き出しは設定先で行う。外部 DB を使う build・参照系は Vault に `.mdhop`・設定・一時ファイル等を作成・変更・削除しない。ノートの変更を目的とするコマンドは Vault 内の対象を変更する。build の一時 DB と SQLite の補助ファイルを含む索引生成の書き込みは DB 側で完結させる。指定 DB と同じディレクトリで一時 DB を完成させ、成功時だけ置き換え、失敗時は既存 DB を保持する。

  並行参照: 再生成中も既存 DB を参照でき、置換と重なった参照が未完成の DB を観測しないことを確認する。置換前から開いている接続と置換後に開始する参照の挙動、対応 OS 上の制約を検証して明記する。複数回の CLI 呼び出しで同一世代を参照する保証や、DB と変更中の本文の同時点保証は加えず、本文プレビューの既存の stale 検査を維持する。build と update 等の同時書き込みの扱いも、並行読み取りと区別して明記する。

  受入条件: 対象の全コマンドで指定先を使い、相対パスの基準・引数省略・設定なし・既定設定・任意名の設定を確認する。既定ファイルと明示指定ファイルが両方あっても明示した一つだけを読む。読取専用の対象フォルダから外部 DB を生成・参照でき、処理中の書込権限が不要で前後のファイル集合と内容が変わらない。再生成失敗後も旧 DB が利用でき、並行参照で完成済み索引だけが見える。CLI ヘルプ・README と関連する現行 ADR を更新する。

- [x] 索引 DB の既定保存先をユーザーのキャッシュ領域に変更する

  保存先: `--db` がない場合は `<cache>/mdhop/vaults/<Vault root のハッシュ>/index.sqlite` を使う。`<cache>` は絶対パスの `XDG_CACHE_HOME` とし、未設定・空・相対パスの場合は `~/.cache` を使う。Vault root は絶対パス化して symlink を解決した実体のパスから識別し、同じ対象は同じ保存先にする。異なる索引設定の DB を同じ Vault で併用する場合は `--db` で保存先を分ける。

  動作: Vault の移動でパスが変われば別の索引として再生成する。キャッシュが削除された場合は build による再生成を案内する。実効的な Vault・設定・DB のパスを確認できる手段を用意する。旧 `<vault>/.mdhop/` からの移行・削除は `migrate` が担い、通常操作では自動移行しない。

  受入条件: 全 DB 操作が同じ既定保存先を使い、環境変数の有無・同じ実体への別パス・Vault 移動・キャッシュ欠落・`--db` による明示指定を確認する。CLI ヘルプ・README と関連する現行 ADR を更新する。

  範囲外: 自動更新、DB の世代管理・保持数・自動削除、管理 UI、DB なしのリンク解決。既定領域の DB 一覧は v0.23.0 の別タスクで扱う。

- [x] `migrate` で既存の YAML 設定と Vault 内 DB を新しい既定配置へ移行する

  操作: `mdhop migrate [--vault <path>]` とし、未指定時はカレントディレクトリを対象にする。`--db`・`--config` は受け付けない。対象は `<vault>/mdhop.yaml`、`<vault>/mdhop.toml`、`<vault>/.mdhop/` と、その Vault に対応する既定キャッシュ DB に固定する。

  処理: 既存 YAML 設定を同じ意味の TOML に変換・検証して保存し、その設定で既定キャッシュ領域へ索引を全量再生成する。設定がもともとなければ設定なしの既定値で再生成する。再生成に成功してから旧 YAML 設定と `<vault>/.mdhop/` を削除する。既存の TOML を意図せず上書きせず、変換不能な設定を黙って落とさない。変換・保存・再生成に失敗した場合は旧 YAML と `.mdhop/` を保持し、後始末の失敗時も残った状態を報告する。

  受入条件: カレント・`--vault` の両方から実行でき、変換後の設定とキャッシュ DB で通常の参照コマンドが動く。成功時に旧 YAML と `.mdhop/` がなくなり、削除後の最終的なファイル集合と索引が整合する。失敗時に旧設定・旧 DB を失わない。`--db`・`--config` を拒否する。CLI ヘルプ・README に移行手順と失敗時の扱いを記載する。

- [x] 行番号付き resolve の採否と、同じ原文のリンクを出現位置で区別する契約を判断する

  目的: 同じノートにある同じ原文 `[[x\|表示文字列]]` が表内では `x.md`、表外では `x\.md` を指す場合に、クリックした側の解決先を返せるようにする。元ノートと原文だけでは区別できない出現文脈を渡す方法を検討し、リンク構文の意味を変えることは前提としない。

  完了: 任意の `--line` を採用し、列位置・文字オフセットは追加しないと判断した。理由と責任境界は [ADR 0035](../decisions/0035-line-qualified-resolve.md)に記録した。未実装の契約・受入条件は [今後の検討](#今後の検討)の独立した実装タスクに置き、実装版は未確定とする。

### v0.23.0

- [ ] mdhop の既定キャッシュ領域に保存された索引 DB と対象 Vault のパス一覧を返す

  目的: Vault root のハッシュで保存される DB の場所と対象フォルダを利用者・エージェントが確認できるようにする。

  対象: 現在の `XDG_CACHE_HOME`（未設定・空・相対パスなら `~/.cache`）の `mdhop/vaults/` 配下にある索引を一覧する。各項目は DB の絶対パスと対応する Vault root の絶対パスを返す。ハッシュから元パスは復元できないため、既定領域の索引生成時に一覧に必要な対応情報を保持する。

  境界: `--db` で指定された外部 DB の登録・追跡・横断探索はしない。過去の `XDG_CACHE_HOME` の探索や自動削除も行わない。

  受入条件: 複数の Vault の既定 DB と対象パスを対応付けて一覧でき、既定キャッシュ領域外の DB は含まれない。キャッシュが存在しなければ空の一覧を返し、一覧操作でディレクトリや DB を作成しない。一時 DB・SQLite 補助ファイルを別の索引として数えない。text / JSON 出力を用意し、コマンド名・出力項目・順序を CLI ヘルプとテストで定める。

### 今後の検討

- [ ] resolve に任意の行番号を指定し、索引のリンク出現を選択する

  目的: [ADR 0035](../decisions/0035-line-qualified-resolve.md)の採用判断に従い、同一ノートの同じ raw が表内外で異なる意味を持つ場合にクリックした行の解決先を返す。v0.22.0 の採否調査とは独立した未実装タスクで、版は未確定とする。

  契約:

  - `resolve --from <vault-relative-note> --link <indexed-raw-text> --line <positive-integer>`。`--line` は任意で、明示時は 1 以上の整数だけを許す。0・負数・整数でない値は引数エラーとし、省略と明示 0 を区別する。
  - 行はファイル先頭を 1 とする元の物理行番号で、frontmatter も数える。表示上の行・折返し行ではない。現在の単一行本文リンクの出現行、索引の `line_start` への完全一致を用い、範囲包含・近傍探索はしない。参照リンクは定義行でなく使用箇所の行を指定する。
  - 指定時は正規化された元ノート・`raw_link` の完全一致・`line_start` の一致を満たす edge だけを選ぶ。呼び出し元は escape / alias / embed / fragment / 空白を勝手に除去・正規化しない。タグ等も含め、既存索引の `raw_link` 表現は変えない。
  - distinct な `target_id` と `COALESCE(subpath, '')` の組が一つなら成功し、同じ組の複数出現も成功する。異なる target または subpath が複数なら `ErrAmbiguousLink`、ゼロ件なら `ErrLinkNotFound` 相当の解決エラーとする。別行・再解析・正規化照合へフォールバックしない。source 未登録等の既存エラー処理は維持する。
  - 省略時は既存の完全一致優先、異なる索引意味の拒否、完全一致がない場合の既存再解析照合を維持する。既存の出力項目と text / JSON の形を維持する。
  - 呼び出し元は同じ Vault / DB を選び、索引作成時と同じ保存済み本文から元ノート・raw・物理行を取得する。保存後に `build` または適切な `update` / `add` 等を完了し、位置を取得し直す。参照定義・表境界の編集も索引更新が必要で、設定・解析規則の変更時は `build` する。未保存 buffer、原文へ逆対応できない renderer、行移動後の古い索引には正しいクリック先を保証しない。
  - 行と原文の一致だけでは本文と索引の同一世代を証明できない。位置取得から解決まで本文・索引を変更しないことを利用条件とし、本文再読・mtime/hash 検査・世代 token・自動更新・排他制御や並行編集・更新をまたぐ snapshot 保証を追加しない。

  実装範囲: `cmd/mdhop/resolve.go` の flag 解析・help、README 日英、`internal/core/resolve.go` の位置指定経路・feature SQL、対象 core / CLI テスト。core API の具体的なシグネチャは既存 caller と `Locations` の互換性を確認して選ぶ。schema・parser・dispatcher・列/offset API・呼び出し元 UI / renderer は変更しない。frontmatter や未対応の複数行文法の保証も広げない。

  受入条件: 表内外の同一 raw を行別に解決でき、frontmatter を含む物理行番号と参照リンクの使用行を扱う。同一行の同結果の重複は成功し、異なる target / subpath は拒否する。raw 不一致・行不一致は別行や再解析に逃げずエラーになる。無効な `--line` と明示 0 を拒否する。行省略時の既存互換、本文を編集しても未更新なら索引 snapshot に依存する挙動、既存 text / JSON 形をテストする。同一行の異なる意味を通常の parser で生成できなければ core の索引 fixture で確認し、文法を拡張しない。

  検証: [検証手順](../docs/verification.md)の core / CLI 変更 gate に従い、集中テスト、`go test ./...`、`go build ./...` と実バイナリの正常系・異常系（stdout・stderr・終了コード・file / DB の副作用）を確認する。help / README に物理行・原文・索引整合の利用条件を記載する。

- [ ] 全量 build と変更検出・差分反映を比較し、自動差分更新を追加する価値を判断する

  目的: 索引を繰り返し更新する際の待ち時間を減らす価値があるかを判断する。利用者が更新対象を列挙せずに索引を最新化する操作について、現行の全量 build で十分か、変更検出を含む差分反映に実用上の利点があるかを判断する。差分機能の実装を前提にせず、採用しない判断も完了とする。

  調査: 代表的な Vault と規模・本文量・変更割合を変えたケースで、現行 build の列挙・ファイル読み取り・解析・DB 作成にかかる時間を測る。更新時刻等の確認コストも含めて、全量 build、既存の status と update / add 等の組み合わせ、自動差分反映の最小案を比較し、削減できる時間・必要になる保守負担・利用頻度を整理する。実測上十分速い場合は現行方式を維持する。

  検討事項: 「前回 build 時刻より mtime が新しいファイルだけ」では、削除、mtime を保持した追加・移動・復元、同一秒の変更、build 中の変更を取りこぼし得る。既存のファイル別 mtime を用いる方法との違いと、保証できる範囲を確認する。また、変更していないノートでも、参照先の追加・削除や basename 衝突で解決結果が変わること、設定・解析規則・索引形式の変更では全量再生成が必要になることを踏まえ、全量 build と同じ関係を保つために必要な処理を評価する。

  完了: 測定条件と結果、採用 / 見送りの判断と根拠をまとめる。採用する場合は、解決する利用上の問題、最小の操作・変更検出規則、全量 build へ戻す条件と受入条件を明確にし、実装を別タスクとして起票する。
