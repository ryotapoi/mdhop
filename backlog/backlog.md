# Backlog

## 運用ルール

- Backlog には、今後着手でき、完了を判定できる作業を `- [ ]` 形式のタスクとして置く。
- 対応要否を決める調査もタスクにできる。観察事実だけを残さず、判断したい問いと、判断をもって完了とすることを明示する。
- 粗いメモで起票してよいが、着手前に目的と受け入れ条件を読める粒度へ詰める。
- バージョン番号を付ける場合は SemVer に従う。
- タスクは `###` 見出しでグループに分ける。バージョンが確定したグループだけ、`### v0.11.0 名前` のように見出しへ番号を付ける。
- グループが大きい場合は、`####` 見出しでさらに分割してよい。

### v0.21.0 リンク解釈の正確性

#### 不具合修正

- [ ] Markdown リンクのエスケープ・文字参照・URL エンコードと、表内 wikilink の alias を正しく解釈する

  目的: Markhop などの利用側がリンク原文を mdhop に渡すだけで、対応する Markdown 記法の意味に沿った移動先を取得できるようにする。索引生成時の関係取得と resolve の両方で同じ解釈を使い、利用側に独自 resolver や復号による補完を要求しない。

  現状: Markhop 同梱の v0.19.1 で報告された以下のケースは、HEAD `4313943`（`v0.19.6-9-g4313943`）でも再現した。索引と resolve が別々の結果を返すのではなく、両方が同じ誤った解釈をしている。特に `A B.md` と `A%20B.md` が共存すると、`[表示](A%20B.md)` が後者へ誤接続する。

  受入条件の起点となる例:

  - `[表示](a\(b\).md)` は `a(b).md` を参照する。
  - `[表示](A&amp;B.md)` は `A&B.md` を参照する。
  - `[表示](A%20B.md)` は `A B.md`、`[表示](A%2520B.md)` は文字列として `%20` を含む `A%20B.md` を参照し、両方が共存しても混同しない。
  - GFM 形式の表内にある `[[X\|表示]]` は参照先 `X`、表示名「表示」として解釈する。

  着手時に確定する仕様・範囲:

  - 対応する構文と基準を整理する。通常の Markdown リンク、image、参照リンクの定義 destination への適用範囲を決める。参照リンクの現行仕様にある escape / entity 非対応の制限との整合も取る（`docs/specs/overview.md`）。wikilink や frontmatter の raw path に Markdown destination の復号を一律適用しない。
  - backslash escape、文字参照、percent decode の順序・各段階の回数と、fragment 分離・外部 URI 判定・パス正規化・Vault 外参照検証との関係を定める。復号後の値を再び原文として復号せず、encoded delimiter と構文上の delimiter を区別する。
  - 表内の `\|` を扱う文脈と、表外の wikilink の規則を決める。resolve がリンク原文と source / 保存 edge から表の文脈をどう取得するか、同じ原文が異なる文脈に現れる場合にどう扱うかも確定する。
  - リンク原文・位置情報を保持し、解決用の値と区別する。変更した解釈を直接使う書き換え経路で、alias / subpath / embed と参照先の意味を保つ再出力規則を定める。参照定義の自動 rewrite など、既存の非対応機能をこのタスクだけで拡張しない。
  - 既存索引に保存された旧解釈との互換性と、再 build の要否・要求方法を決める。CLI / JSON は既存インターフェースを起点とし、変更が必要なら理由と範囲を明示する。

  完了: 上記の仕様・受入条件・実装範囲を確定して正本へ反映し、例の実在 target と未作成 target の双方で build / update、resolve、outgoing / backlinks が同じ参照先を扱うことを検証する。通常リンクと同じ関係として 2-hop に反映されること、変更した解釈に直接関わる書き換え後の再解析でも参照先と構文上の意味が保たれることを確認する。

  出典: Markhop からのリンク解釈相談と現行 HEAD での再現確認。未リンク言及の探索は別途検討する。

### 関連表示と 2-hop のフィルタ整理

- [ ] query の表示非表示と 2-hop の手がかり選択を分離し、指定した共通ターゲットから関連ノートを取得できるようにする

  目的: Markdown ファイルを開いて関連ノートを読む際に、一覧の表示を減らす操作と、関連性の根拠に使う共通ターゲットを選ぶ操作を独立して使えるようにする。表示したくないノートやタグを隠しても、それを介した関連ノートまで失われないようにする。

  このタスクは実装に着手するための要求・検討事項・受入条件をまとめたもので、現行仕様の正本を置き換えない。着手時に未決事項と互換性方針を確定し、実装・検証と正本への反映まで行う。バージョンは未定。

  変更方針: 今回の整理では既存仕様の変更を許容し、後方互換性の維持を必須条件にしない。要求に沿って CLI / config / JSON の意味や形式を変更できる。旧仕様を残すためだけの別名・互換処理は必須にせず、採用した変更点と利用側の移行方法を明記する。個別機能の削除や 1.0.0 への移行は、この方針だけで決定したものとは扱わない。

  **利用場面と関係の意味**

  - 主な入口は、開いている Markdown ファイル B。backlinks は B へリンクするノート、outgoing は B が参照する note / asset / phantom、tags は B が持つタグとして読む。
  - 2-hop は共通ターゲット方式の `B → X ← C`。X を関連を見つける「手がかり」とし、C を関連ノートとして返す。通常の backlinks / outgoing に via の概念を導入しない。
  - 現行の tag / phantom / asset など非 note の入口に対する処理は、既存の inbound seed を確認して互換性を定める。主な要求を Markdown 入口で満たすために、新しい探索方式や入口なしの検索を追加しない。

  **表示から隠す操作**

  - パス条件に一致する Markdown ファイルと、タグを関連表示から隠せるようにする。例は `archive/*` のノートや `#daily` のタグ。「タグを隠す」が tags 表示全体を隠す操作と個別タグを条件で隠す操作のどこまでを含むか、その指定方法を着手時に確定する。どちらも、そのタグを持つノートをすべて隠す意味にはしない。
  - 表示非表示は 2-hop の関係計算を変えない。X を隠しても `B → X ← C` による C は残り、C 自身を隠した場合は C を表示しない。
  - 同じノートが backlinks / outgoing / twohop の複数箇所に現れる場合も、表示非表示を一貫して適用する。入口 B 自体を隠す条件に一致させた場合の扱いは、入口を除外しない現行契約を起点に定める。
  - Markdown ファイルを隠す要求を asset / phantom の非表示へ暗黙に拡張しない。現行のパスを持つ node と持たない node の扱いを確認し、今回の操作の適用型と互換性を明記する。
  - 外部 URL はグラフの管理対象ではないため、URL 非表示や外部リンクの索引化は追加しない。

  **2-hop の手がかりを選ぶ・除く操作**

  - 表示非表示とは別のオプション群で、共通ターゲットとして使うパス・タグの包含条件と除外条件を指定できるようにする。条件未指定時は通常の共通ターゲット探索を保つ。
  - パスパターンによる包含だけでなく、単一の共通ターゲット X を明示指定できるようにする。B と X を指定すると `B → X ← C` による C を返し、B が X を参照していない場合は空結果とする。別の X への fallback はしない。
  - B を指定せず X の inbound 全体を探す操作は、既存の backlinks に相当するため、このタスクで新設しない。
  - 単一 X の指定とパスパターンの指定を区別し、note のパスと tag の型を含む安定した識別方法を決める。同じ綴りの note と tag を混同しない。
  - 複数の包含条件は OR とし、除外条件のいずれかに一致すれば除外を優先する。包含・除外を同時に指定した場合も、許可された手がかりだけを使う。
  - 手がかりの包含・除外と表示非表示は独立して合成する。X を表示から隠しながら手がかりとして選べること、X を手がかりから除いても通常の outgoing の表示まで消えないことを保証する。

  **条件の表記と CLI / config の整理**

  - 名称案は表示側の `--hide-path 'archive/*'` / `--hide-tag '#daily'` と、手がかり側の `--via-path 'docs/*'` / `--exclude-via-path 'archive/*'` / `--via-tag '#daily'` およびタグ除外の対になるオプション。これらは命名案であり、採用する flag 名や単一 X の構文は着手時に決める。
  - 両オプション群は、同種の条件に同じ照合規則を使う。パスは現行の Vault 相対パス・正規化と glob を起点にし、`*` は `/` を含む任意文字列、`?` は一文字、case-sensitive、`[...]` は非対応とする。タグは `#` の正規化と case-insensitive な完全一致を起点にする。
  - 任意の名前正規表現や、新しいメタデータ条件を追加する要求は含めない。必要なパス条件・タグ条件・単一 X の識別に絞る。
  - 現行の `--exclude` は twohop の via と targets の両方を除き、`--exclude-tag` は tags の表示と twohop の via / tag target に影響する。この意味をどう移行するかを決め、既存 flag の意味変更・別名維持・削除・新名称への移行を区別する。
  - `mdhop.yaml` の `exclude` と CLI 除外のマージ、`--no-exclude` による config 無視の現行契約を踏まえ、新しい二つの目的を設定でどう表すかを決める。既存利用者にとって同じ設定が何を変えるかを説明できる状態にする。
  - `--path` / `--where` は現行では結果ノード側の条件で、via の選択ではない。残す・変更する範囲を明確にし、今回の要求だけを理由に `--where` などの既存機能を一括削除しない。
  - 仕様や機能の削除も選択肢だが、特定機能の削除はまだ決定していない。共有 helper を使う search / diagnose / reachable / graph などを、query と同じ名称・意味へ自動的に変更しない。直接影響する契約だけを確認・修正する。

  **frontmatter と対象範囲**

  - frontmatter 由来の通常リンクは、設定された raw path を含め、本文リンクと同じ関係として表示非表示・手がかり選択を適用する。frontmatter 専用の非表示操作は追加しない。
  - リンクになっていない通常の frontmatter 値は関係表示の対象ではない。meta / head / snippet の設計変更は今回の主題に含めず、共有フィルタ変更で直接影響する既存の出力契約のみ保つ。
  - `--link-key` の削除は決まっていない。direct な backlinks / outgoing を frontmatter key 由来のリンク出現に限定し、twohop には適用しない現行契約を確認し、残す場合は今回の操作との組み合わせを検証する。

  **着手時に解決する出力・上限の事項**

  - 現行 JSON は twohop を `via` と `targets` の組で返す。非表示にした X を出力で露出させずに C と関連理由をどう伝えるかを決める。X の代替表示や匿名化を、すでに決定した仕様として扱わない。
  - C に複数の手がかりがある場合、表示可能な手がかりと非表示の手がかりが混在する場合、すべての手がかりが非表示の場合を含め、理由・重複・グループの表現を決める。JSON の schema / fields と text 出力の互換性を明記する。
  - 手がかり選択、表示非表示、結果側の条件、並び順、`--max-backlinks` / `--max-twohop` / `--max-via-per-target` の適用順と件数の数え方を定める。非表示の結果や、許可された表示対象を持たないグループが上限枠を消費して、後続の有効な結果を欠落させないようにする。
  - 同じ結果を後処理と再取得で別々の条件から計算したり、一部の node 型だけに新条件が適用されたりしないよう、採用した適用型・順序を通常経路で検証する。
  - stdout の JSON を単独で parse できる安定インターフェースとして扱い、warning や移行案内などの付加情報は stderr に出す。出力変更が必要なら、その理由と利用側の対応を正本に反映する。

  **受入条件**

  - 基本 fixture を `B → X ← C` と `B → Y ← D` とする。X は `archive/X.md` に置き、C も必要に応じて archive 配下に置く。条件未指定時には現行の関係を取得できる。
  - X だけを表示から隠した場合は C が残り、C を隠した場合は C が消える。X を手がかりから除いた場合は X 経由の C が消え、Y 経由の D は残る。X を明示的に選んだ場合は C を取得し、D を取得しない。
  - B が参照していない共通ターゲットを明示した場合は空結果になる。単一 X と glob による包含を区別でき、同名 note / tag の指定がそれぞれ意図した型に解決される。
  - C が X と Y の両方を介して B に関連する fixture で、包含の OR、除外の優先、表示条件との合成を確認する。X を除いても Y が許可されていれば C は残り、C 自身を隠せば両経路で表示されない。
  - 共通タグ `#daily` を持つ B と C で、採用した tags 表示全体・個別タグの非表示操作だけでは C が消えず、手がかりのタグ除外ではそのタグ経由の関連が消える。タグを隠しても、そのタグを持つ通常の backlinks / outgoing のノートは一律に消えない。
  - 本文と frontmatter の通常リンクで同じ表示条件・手がかり条件が同じ結果になる。frontmatter の通常値から新たな関係を作らず、直接影響する既存の `--link-key` / `--path` / `--where` 契約を確認する。
  - 上限より前に非表示結果や空グループが多数ある fixture でも、上限まで取得可能な有効結果があれば欠落せずに返す。複数手がかり・非表示の手がかりだけが残る結果について、決定した理由表現・順序・件数を確認する。
  - 既存 config と CLI の組み合わせ、`--no-exclude`、パスの大小文字・`/` を含む glob・非対応文字クラス、タグの `#` 有無・大小文字、適用対象となる note / asset / phantom / tag の正常系と異常系を検証する。

  **実装の入口と完了条件**

  - 入口は `internal/core/query.go` / `query_fetch.go`、`exclude_filter.go` / `pathfilter.go`、`cmd/mdhop/query.go` / `format_query.go` と関連 query test。現行契約は `docs/specs/overview.md`、責務と依存方向は `docs/rules/architecture.md`、保存形式へ影響する場合は `docs/rules/03-data-model.md` を確認する。
  - 完了: 未決の CLI / config・適用型・非表示 via の理由表現・互換性・上限規則を確定し、要求を満たす最小の整合した実装を行う。採用した振る舞いを正本へ反映し、判断理由を残す必要がある場合は decisions の運用に従う。このタスク本文を恒久仕様として残すことで完了にしない。
  - 検証は `docs/rules/verification.md` に従い、集中 test、`go test ./...`、`go build ./...` と実バイナリによる CLI 確認を行う。影響する正常系・異常系で stdout / stderr / 終了コードと、query が索引やファイルを変更しないことを確認する。

### 今後の検討

- [ ] 全量 build と変更検出・差分反映を比較し、自動差分更新を追加する価値を判断する

  目的: Markhop アプリから気軽に索引を更新する際の待ち時間を減らす価値があるかを判断する。エージェントによる利用では全量 build で十分でも、アプリの繰り返し操作では応答時間の差が重要になり得る。利用者が更新対象を列挙せずに索引を最新化する操作について、現行の全量 build で十分か、変更検出を含む差分反映に実用上の利点があるかを判断する。差分機能の実装を前提にせず、採用しない判断も完了とする。

  調査: 代表的な Vault と規模・本文量・変更割合を変えたケースで、現行 build の列挙・ファイル読み取り・解析・DB 作成にかかる時間を測る。更新時刻等の確認コストも含めて、全量 build、既存の status と update / add 等の組み合わせ、自動差分反映の最小案を比較し、削減できる時間・必要になる保守負担・利用頻度を整理する。実測上十分速い場合は現行方式を維持する。

  検討事項: 「前回 build 時刻より mtime が新しいファイルだけ」では、削除、mtime を保持した追加・移動・復元、同一秒の変更、build 中の変更を取りこぼし得る。既存のファイル別 mtime を用いる方法との違いと、保証できる範囲を確認する。また、変更していないノートでも、参照先の追加・削除や basename 衝突で解決結果が変わること、設定・解析規則・索引形式の変更では全量再生成が必要になることを踏まえ、全量 build と同じ関係を保つために必要な処理を評価する。

  完了: 測定条件と結果、採用 / 見送りの判断と根拠をまとめる。採用する場合は、解決する利用上の問題、最小の操作・変更検出規則、全量 build へ戻す条件と受入条件を明確にし、実装を別タスクとして起票する。
