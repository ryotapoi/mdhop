## タスク

### 仕様検討

- [ ] `#a//b` のように空の階層を含むタグの扱いを決める
  - 目的: mdhop は空の階層を詰めて `#a/b` として索引するが、Obsidian は `#a//b` を `#a/b` とは別の、名前が空の階層を含むタグ（`a` → 空 → `b`）として扱う（2026-11-26 にタグ一覧で確認）。詰める処理は Obsidian 互換のタグパーサー（21c68a5）で入ったが、テストも ADR もない。この結果、`--include-location` で `#a//b` の位置が見つからない、または同じ行の別のタグの位置を返す。
  - 完了条件: Obsidian に合わせるか、別の規則に整理し直すかを決める。
  - 未決の問い: 名前が空の階層を mdhop でどう表すか。タグの `raw_link` が原文でなく生成したタグ名であること（ADR 0035）も合わせて見直すか。
  - 手がかり: `internal/core/parse.go:413–420`、`internal/core/query_location.go:193–211`。全体の見直しのときに扱う。どちらに決めても再 build が要る。

- [ ] リンク位置を返してよい「索引とファイルが一致している」状態を決める
  - 目的: `--include-location` は、索引の秒単位の更新時刻と今のファイルを比べて、変わっていなければ位置を返す。同じ秒の中でリンク先を書き換えると気付かず、古いリンク先の結果に今の位置を付ける（例: `[ref]: E.md` を同じ秒に `[ref]: F.md` へ変えると、E への backlink に `[ref]` の位置を返す）。build はファイルごとにナノ秒の更新時刻とサイズを記録しているが、update・add・move・delete の後は次の build まで使えない。秒単位の比較は以前からの抜粋（`--include-snippet`）の判定と同じ規則。
  - 完了条件: 位置を返す条件を決める。mutation コマンドの後に位置がどこまで出るかも含める。
  - 手がかり: `internal/core/query_location.go:136–159`、`internal/core/build_incremental.go:17–22,308–319`、ADR 0038（編集の完全な検知は保証しない）。

- [ ] 行をまたぐインラインコードをどう解釈するか決める
  - 目的: CommonMark では、段落の中のインラインコードは改行をまたげる。mdhop の共有パーサーは1行単位で判定するため、mentions がコードの中の名前を言及として返し、閉じた後ろの言及を落とすことがある。索引の作成も同じ判定を使う。
  - 完了条件: 行をまたぐインラインコードを除くか、1行だけ扱うと明記するかを決める。
  - 手がかり: `internal/core/parse.go:84–155,198–241`。共有パーサーを変える場合は再 build が要る。

- [ ] frontmatter の同じ行に複数のリンクがあるときの `raw_link` を決める
  - 目的: `related: ["./E.md", "[[E]]"]` の backlink で、`raw_link` は左の `./E.md` でなく右の `[[E]]` になる。索引が wikilink をパスより先に登録するため。ヘルプは同じ行の中では左端のリンクを選ぶと書いている。
  - 完了条件: 左端を優先するか、索引の順になると明記するかを決める。左端を優先する場合は、YAML の値と位置の対応付けが要る。
  - 手がかり: `internal/core/parse.go:192–195`、`internal/core/parse_frontmatter.go:65–96,207–244`、`internal/core/query_location.go:35–43,86–94`。

- [ ] 仕様の整理の後に、位置付き query の性能を改善する
  - 目的: 位置取得の処理には、出力を変えずに減らせる処理が残っている。
    - 2-hop で、同じ段落の解析を経由ノートの数だけ繰り返す（1つの段落に経由ノート 2,048 件で 0.97 秒、位置なしで 0.017 秒）。
    - 2-hop の組ごとに SQL を1回発行する（対象 100 件 × 経由ノート 33 件で 3,300 回、CLI 全体の中央値が 15.4 ms から 83.7 ms）。
    - 位置・抜粋・冒頭を同時に指定すると、同じ本文を別々に読んで保持する（400 ノートでピーク RSS が位置だけ 244.0 MiB、3つすべて 369.6 MiB）。
  - 対応: improve-performance を使って計測・比較する。
  - 完了条件: 出力が変わらず、同じ例で時間とメモリが下がる。
  - 手がかり: `internal/core/query_preview.go:20–92`、`internal/core/query_location.go:35–60,153–185`、`internal/core/query_content.go:53–73,116–128`。

- [ ] 1回のコマンドの中で、索引の一貫性をどこまで保証するか決める
  - 目的: mentions は1回の実行の中で、索引に何度か別々に問い合わせる（リンク済みのノート、`--where` の絞り込み、並べ替えの値）。その間に別のプロセスの update が書き込むと、問い合わせごとに更新前と更新後の値が混ざり、条件に合わないノートが結果に入りうる（同じ接続で2つの問い合わせの間に update を挟んで再現）。読み取りにトランザクションを使っている箇所はなく、query と search も同じ。ADR 0038 は build と update の同時書き込みを未サポートとするが、読み取りと書き込みの並行は決めていない。
  - 完了条件: 読み取りを1つのトランザクションにまとめて同じ時点の索引を読むか、呼び出す側に直列化を求めて明記するかを決める。
  - 未決の問い: 読み取りのトランザクション中は、今の SQLite の設定では update の書き込み確定が待たされるか失敗する。それを受け入れるか、設定を変えるか。
  - 手がかり: `internal/core/mentions.go:126–134,244–275,305–345`、`internal/core/update.go:132–164`。
