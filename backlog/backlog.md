### v0.23.0

- [ ] mdhop の既定キャッシュ領域に保存された索引 DB と対象 Vault のパス一覧を返す

  目的: Vault root のハッシュで保存される DB の場所と対象フォルダを利用者・エージェントが確認できるようにする。

  対象: 現在の `XDG_CACHE_HOME`（未設定・空・相対パスなら `~/.cache`）の `mdhop/vaults/` 配下にある索引を一覧する。各項目は DB の絶対パスと対応する Vault root の絶対パスを返す。ハッシュから元パスは復元できないため、既定領域の索引生成時に一覧に必要な対応情報を保持する。

  境界: `--db` で指定された外部 DB の登録・追跡・横断探索はしない。過去の `XDG_CACHE_HOME` の探索や自動削除も行わない。

  受入条件: 複数の Vault の既定 DB と対象パスを対応付けて一覧でき、既定キャッシュ領域外の DB は含まれない。キャッシュが存在しなければ空の一覧を返し、一覧操作でディレクトリや DB を作成しない。一時 DB・SQLite 補助ファイルを別の索引として数えない。text / JSON 出力を用意し、コマンド名・出力項目・順序を CLI ヘルプとテストで定める。

### 今後の検討

- [ ] resolve に任意の行番号を指定し、索引のリンク出現を選択する

  目的: [ADR 0035](../decisions/0035-line-qualified-resolve.md)の採用判断に従い、同一ノートの同じ raw が表内外で異なる意味を持つ場合にクリックした行の解決先を返す。v0.22.0 の採否調査とは独立した未実装タスクで、版は未確定とする。

  契約:

  - `resolve --from <vault-relative-note> --link <indexed-raw-text> --line <positive-integer>`。`--line` は任意で、明示時は 1 以上の整数だけを許す。0・負数・整数でない値は引数エラーとし、省略と明示 0 を区別する。
  - 行はファイル先頭を 1 とする元の物理行番号で、frontmatter も数える。表示上の行・折返し行ではない。現在の単一行本文リンクの出現行、索引の `line_start` への完全一致を用い、範囲包含・近傍探索はしない。参照リンクは定義行でなく使用箇所の行を指定する。
  - 指定時は正規化された元ノート・`raw_link` の完全一致・`line_start` の一致を満たす edge だけを選ぶ。呼び出し元は escape / alias / embed / fragment / 空白を勝手に除去・正規化しない。タグ等も含め、既存索引の `raw_link` 表現は変えない。
  - distinct な `target_id` と `COALESCE(subpath, '')` の組が一つなら成功し、同じ組の複数出現も成功する。異なる target または subpath が複数なら `ErrAmbiguousLink`、ゼロ件なら `ErrLinkNotFound` 相当の解決エラーとする。別行・再解析・正規化照合へフォールバックしない。source 未登録等の既存エラー処理は維持する。
  - 省略時は既存の完全一致優先、異なる索引意味の拒否、完全一致がない場合の既存再解析照合を維持する。既存の出力項目と text / JSON の形を維持する。
  - 呼び出し元は同じ Vault / DB を選び、索引作成時と同じ保存済み本文から元ノート・raw・物理行を取得する。保存後に `build` または適切な `update` / `add` 等を完了し、位置を取得し直す。参照定義・表境界の編集も索引更新が必要で、設定・解析規則の変更時は `build` する。未保存 buffer、原文へ逆対応できない renderer、行移動後の古い索引には正しいクリック先を保証しない。
  - 行と原文の一致だけでは本文と索引の同一世代を証明できない。位置取得から解決まで本文・索引を変更しないことを利用条件とし、本文再読・mtime/hash 検査・世代 token・自動更新・排他制御や並行編集・更新をまたぐ snapshot 保証を追加しない。

  実装範囲: `cmd/mdhop/resolve.go` の flag 解析・help、README 日英、`internal/core/resolve.go` の位置指定経路・feature SQL、対象 core / CLI テスト。core API の具体的なシグネチャは既存 caller と `Locations` の互換性を確認して選ぶ。schema・parser・dispatcher・列/offset API・呼び出し元 UI / renderer は変更しない。frontmatter や未対応の複数行文法の保証も広げない。

  受入条件: 表内外の同一 raw を行別に解決でき、frontmatter を含む物理行番号と参照リンクの使用行を扱う。同一行の同結果の重複は成功し、異なる target / subpath は拒否する。raw 不一致・行不一致は別行や再解析に逃げずエラーになる。無効な `--line` と明示 0 を拒否する。行省略時の既存互換、本文を編集しても未更新なら索引 snapshot に依存する挙動、既存 text / JSON 形をテストする。同一行の異なる意味を通常の parser で生成できなければ core の索引 fixture で確認し、文法を拡張しない。

  検証: [検証手順](../docs/verification.md)の core / CLI 変更 gate に従い、集中テスト、`go test ./...`、`go build ./...` と実バイナリの正常系・異常系（stdout・stderr・終了コード・file / DB の副作用）を確認する。help / README に物理行・原文・索引整合の利用条件を記載する。

- [ ] 全量 build と変更検出・差分反映を比較し、自動差分更新を追加する価値を判断する

  目的: 索引を繰り返し更新する際の待ち時間を減らす価値があるかを判断する。利用者が更新対象を列挙せずに索引を最新化する操作について、現行の全量 build で十分か、変更検出を含む差分反映に実用上の利点があるかを判断する。差分機能の実装を前提にせず、採用しない判断も完了とする。

  調査: 代表的な Vault と規模・本文量・変更割合を変えたケースで、現行 build の列挙・ファイル読み取り・解析・DB 作成にかかる時間を測る。更新時刻等の確認コストも含めて、全量 build、既存の status と update / add 等の組み合わせ、自動差分反映の最小案を比較し、削減できる時間・必要になる保守負担・利用頻度を整理する。実測上十分速い場合は現行方式を維持する。

  検討事項: 「前回 build 時刻より mtime が新しいファイルだけ」では、削除、mtime を保持した追加・移動・復元、同一秒の変更、build 中の変更を取りこぼし得る。既存のファイル別 mtime を用いる方法との違いと、保証できる範囲を確認する。また、変更していないノートでも、参照先の追加・削除や basename 衝突で解決結果が変わること、設定・解析規則・索引形式の変更では全量再生成が必要になることを踏まえ、全量 build と同じ関係を保つために必要な処理を評価する。

  完了: 測定条件と結果、採用 / 見送りの判断と根拠をまとめる。採用する場合は、解決する利用上の問題、最小の操作・変更検出規則、全量 build へ戻す条件と受入条件を明確にし、実装を別タスクとして起票する。
