# Review (goal)

## Intent

変更が要求・仕様・既存設計を壊していないことを、作業リスクに応じた深さで確認する。

## Review Mode

- **self-check**: Small 変更（`default.md` の Intake 分類）。自分で diff、要求、検証結果を照合する。下記の並列レビュー手順はスキップ
- **並列レビュー**: 非 Small。下記の手順 0〜5 を実施する

## Decision Criteria

- review は粗探しではなく、実害・仕様逸脱・テスト不足・設計劣化を探す
- 指摘に対応しない場合は、理由をコンテキスト上 plan / commit body / 該当ドキュメントに記録する

## 用語

- **指摘あり観点**: 前周で `needs_action=YES`（1 件以上の MUST/SHOULD 指摘）を返した観点
- **LGTM 観点**: 前周で `needs_action=NO`（指摘ゼロ）を返した観点

## 並列レビュー手順

### 0. 前提整備

#### 0-a. ビルドとテスト

```bash
go build ./...
go test ./...
```

失敗したら修正してから次へ進む。

CLI 動作確認は `verify.md` の段階で既に通過している前提。このフェーズでは実行しない（最後の手順でレビュー対応の差分について再判定する）。

#### 0-b. `/simplify` を Subagent 経由で先行実施（1 周目のみ）

`/simplify` はレビュー + 自動修正の混合スキル。並列レビューより**前**に直列で 1 度だけ走らせ、コードを綺麗にした状態で並列レビューに掛ける。再実施（手順 3）でも実行しない。

**main から直接 `/simplify` を呼ばない。** 戻り値が長く、main の発話が「次へ進む」コンテキストから逸れて止まりやすいため、`Agent` ツール（`subagent_type=general-purpose`）に作業を委譲し、**短い続行合図だけ**を main に返させる。

`Agent` 呼び出しの prompt は次のテンプレートを使う:

```text
タスク:
1. Skill ツールで `simplify` を呼び出す（args は空でよい）。simplify は変更コードのレビュー + 自動修正を行う built-in skill。
2. simplify が返した内容を踏まえ、必要なら追加で修正を適用する（simplify 自身が編集を済ませている場合はそのままでよい）。
3. ビルドとテストを `go build ./...` と `go test ./...` で通す。失敗したら修正してから再実行する。

返答ルール（厳守）:
- 本文に simplify の生のレビュー文や指摘の引用を含めない。
- 次の 2 行だけを返す:
  1 行目: `simplify 完了。続けて並列レビュー（手順 1）に進んでください。`
  2 行目: 直前周で適用した変更の超短い要約（1 文 50 字以内、例: 「重複ヘルパー 1 件を統合、未使用変数 1 件削除。」）。変更がなければ「変更なし。」とだけ書く。
- 上記 2 行以外の前置き・要約・確認・質問は一切付けない。
```

`Agent` の戻り値を受け取ったら main は内容を解釈せず、**ただちに手順 1 へ進む**。Agent の戻り値が上記フォーマットを外していても、ビルド・テストが手順 0-a で通っている限り手順 1 へ進む（再呼び出しはしない）。

### 1. 観点を並列で実施する（1 周目）

並列起動するスキル + viewpoint を選ぶ。**1 つのメッセージで Skill tool 並列起動** する。

`/review-code` と `/review-code-mdhop` は viewpoint 指定 worker。引数は `viewpoint=<name> [<PLAN_PATH>]` 形式（plan ファイルがあるならそのパス、なければ省略）。

**`/simplify` はこの並列リストに含めない**（手順 0-b で Subagent 経由の直列実施に切り出してある）。

| 呼び出し | 引数 | 出力形式 |
| --- | --- | --- |
| `/review-code` | `viewpoint=facts [<PLAN>]` | 結果ファイル化 |
| `/review-code` | `viewpoint=design [<PLAN>]` | 結果ファイル化 |
| `/review-code` | `viewpoint=go [<PLAN>]` | 結果ファイル化 |
| `/review-code-mdhop` | `viewpoint=mdhop [<PLAN>]` | 結果ファイル化 |

**`/review-code-codex` は呼ばない**（goal では Codex 系を使わない）。

各スキルの戻り値テキストから `^RESULT_FILE: ` 行と `^SUMMARY: ` 行を抽出する。
- `RESULT_FILE:` の値が `ERROR` で始まる場合、本文がそのまま戻り値内に含まれているのでフォールバックとして扱う

### 2. 1 周目の結果を統合し、まとめて反映する

1. 全スキル実行が完了するまで結果ファイルは Read しない（戻り値の `RESULT_FILE` / `SUMMARY` 行のみ受け取る）
2. 全スキル完了後、結果ファイル化対象のうち `SUMMARY: ... needs_action=YES ...` のものについて、`RESULT_FILE` のパスを Read で読み込む
   - パスが `/tmp/claude/claude-review-results/` 配下であることを確認してから Read する
   - `needs_action=NO` のスキルの結果ファイルは Read しない
3. 結果ファイルから抽出した指摘を一覧し、🔴 MUST / 🟡 SHOULD 指摘の対応方針を自動判断する
4. 対応方針が決まったら Edit に入る。隣接セクションへの修正は 1 つの Edit にまとめる。離れたセクションへの修正は別 Edit のまま
5. 反映完了後、結果ファイルは再 Read しない

判断が必要な指摘で自動判断できないものは `goal-blocked.md` を作成して停止する。判断したがユーザー意図と違う可能性があるものは `goal-decisions.md` に記録する。

### 3. 2 周目（最終）

前周で「指摘あり観点」だった個別レビューのみを **同一ターンで並列起動** する。LGTM 観点はスキップ。`/simplify` は再実施対象に**含めない**。

**手動確認が必要な変更を入れた場合**（CLI 出力・対話的挙動・実 vault/DB への副作用に影響する修正等）→ 並列起動の前にビルド・テスト（手順 0-a）を再度通す。自動テストのみで十分な変更なら省略してよい。

**再レビュー時の引数渡し**: 自然言語で前回指摘 + 対処を渡す。

```text
viewpoint=<name>
プランファイル `<PLAN>` に対する実装を前回の続きで再レビューしてください。
（plan なしの場合: プランなしで git diff を前回の続きで再レビューしてください。）
前回の指摘への対処:
- 🔴 <指摘1の要旨> → <対応内容を1行 or 対応しない理由を1行>
- 🟡 <指摘2の要旨> → ...
新規問題と、対処の妥当性を確認してください。
```

引数本文に「Claude 側の見解」を混ぜず、事実（何を変えたか・どの指摘を残したか）だけ渡す。**要旨 1 行 + 対処 1 行**で十分。

戻りを全部受け取ったら手順 2 と同じ要領で main で統合・反映する。

### 4. 完了判定

2 周目の結果を見て：

- 全観点 LGTM → 完了
- 重大な指摘が残っている → `goal-blocked.md` を作成して停止する

**3 周目以降に入らない**。レビューループは最大2周で終了する。

### 5. CLI 動作確認の再判定

レビュー対応で CLI 出力・対話的挙動・実 vault/DB への副作用に影響しうる変更を入れた場合、実際に `bin/mdhop <args>` を叩いて挙動を確認する（`verify.md` の観点）。実機ユーザー観察が必須なら `goal-blocked.md` を作成して停止する。

自動テストで十分にカバーできる変更のみ、または変更なしの場合はスキップしてよい。

## Acceptance

- 選んだ Review Mode と理由が説明できる
- 指摘があれば対応済み、または対応しない理由が明確
- レビュー後の変更に対して必要な再検証が済んでいる

## Stop Conditions

次の場合は `goal-blocked.md` を作成して停止する。

- 指摘対応が仕様・CLI 挙動・設計方針を変える複数の妥当案で自動判断不能
- レビュー 2 周しても重大な指摘が残る
